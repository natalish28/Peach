# 0008. Peach's core on Google Cloud: Cloud Run, Cloud SQL, Firebase Hosting

Status: accepted (Lab 9) · Date: 2026-11-11

## Context

Peach runs on AWS (Labs 4–8) and is described in Terraform (ADR 0007). Lab 9 asks what it takes to
run the same system on Google Cloud and what it costs. The core is the static Next.js frontend, the
FastAPI API and its PostgreSQL database (users, items, agendas; foreign keys between them; Alembic
migrations). Around it: Cognito sign-in with Google, the weekly report (EventBridge Scheduler/SQS →
Lambda → S3 → Lambda → SES) and the agenda parser (a Lambda calling Bedrock).

## Decision

Move the core: frontend, API, database. Leave sign-in, the report and the parser on AWS. Google
Cloud gets its own Terraform root (`gcp/`), its own HCP Terraform workspace (`peach-gcp`) and its
own state, so one plan cannot break both clouds. HCP Terraform gets Google credentials through
Workload Identity Federation (`gcp/bootstrap/`). No service account key exists.

| Peach on AWS | On Google Cloud | Decision |
| --- | --- | --- |
| S3 + CloudFront + rewrite function | Firebase Hosting | **Replace.** CDN and certificate included, free plan. `cleanUrls` replaces the CloudFront function; a rewrite sends `/api/**` to Cloud Run, so one origin and no CORS. |
| Lambda + function URL (Mangum) | Cloud Run | **Replace.** The `runtime` Docker target Compose already runs (uvicorn on `$PORT`), no adapter. Min 0, max 1 instance, request-based billing. |
| ECR | Artifact Registry | **Replace.** Cleanup policy keeps 2 images, within the free 0.5 GB. |
| Aurora Serverless v2, 0–1 ACU | Cloud SQL for PostgreSQL 17, db-f1-micro, 10 GB SSD | **Replace, stopped when unused** (see below). |
| DynamoDB | Firestore | **Drop.** Peach never used DynamoDB. |
| Cognito user pool + Google | Identity Platform | **Keep on AWS for now.** The API verifies Cognito tokens on Cloud Run unchanged. Identity Platform is a stretch goal. |
| EventBridge Scheduler | Cloud Scheduler | **Keep on AWS** (the report stays). |
| SQS | Pub/Sub / Cloud Tasks | **Keep on AWS.** If the report moves: Cloud Tasks, which is a work queue like SQS. |
| S3 event → Lambda | Cloud Storage + Eventarc → Cloud Run | **Keep on AWS.** |
| SES | none | **Keep SES** (see E-mail). |
| Bedrock (Nova Lite) | Vertex AI (Gemini; Claude via Model Garden) | **Keep on AWS** (see "Not moved"). |
| SSM / Secrets Manager | Secret Manager | **Replace.** One secret, `peach-database-url`, generated by Terraform. |
| CloudWatch Logs | Cloud Logging | **Replace** (automatic for Cloud Run). |
| IAM roles | Service accounts | **Replace.** `hcp-terraform` for Terraform, `peach-api` for the API, `github-deploy` for CI (optional). No Owner or Editor role, no default compute service account. |
| Terraform `aws` provider | `google` + `google-beta` | **Replace.** Same HCL, second workspace. |

### The database

| Option | Latency | Monthly bill (idle) | Code |
| --- | --- | --- | --- |
| Cloud SQL around the clock | ~1 ms in-region, Unix socket via the connector | ≈ $9.37 | none |
| **Cloud SQL, stopped when not used** | same while running; first request after a start waits for the start, so start it a few minutes ahead | ≈ $1.70 (storage only) | none |
| Firestore | low, per document read | $0 within the daily free quota | rewrite the data layer: no joins, no foreign keys, no Alembic; denormalise per screen |
| Keep Aurora, call it from Cloud Run | +20–40 ms per query us-central1 → us-east-1, several queries per request; Aurora is in a private VPC, so a VPN or a public endpoint is needed | ≈ $0.30 + egress | none, but a network project |

**Chosen: Cloud SQL, stopped when not used** (`make gcp-db-stop` / `gcp-db-start`). Peach's data is
relational and its migrations already run on Postgres 17 in Compose. The same SQLAlchemy code runs
unchanged; only `DATABASE_URL` differs (`?host=/cloudsql/<connection>`). Terraform ignores
`activation_policy`, so an apply does not restart a stopped instance. **Data: migrations against the
empty database**, run by the container's entrypoint on start. Aurora is in a private subnet with IAM
authentication, so `pg_dump` from the laptop would need a bastion. The GCP copy is a separate
environment, not a replica.

### E-mail

Keep SES. The report still runs on AWS, so nothing changes today. When the report moves to Cloud
Run, it can still call SES without a stored key: an IAM role in AWS trusts Google's OIDC issuer
(`accounts.google.com`, audience = the `peach-api` service account's unique ID), and Cloud Run
exchanges its Google ID token through `AssumeRoleWithWebIdentity`. This is the same federation as
Part 0, run in the other direction. If we had to leave AWS completely, we would use Mailgun. Its API key
would be a Secret Manager secret, readable only by the report job's service account and mounted as
an environment variable. It would never go in Terraform variables or the repository.

### Not moved, and why

- **Cognito sign-in.** The user pool holds the accounts. Moving them means exporting users and
  re-linking Google identities. Users would also see a second consent screen, all to save $0: both
  services are free at this size.
- **The agenda parser.** It runs outside the VPC, keeps no state and already accepts calls from any
  origin with a Cognito token, so the Firebase frontend uses it as it is. The trial credit does not
  pay for Claude on Vertex AI, and Nova Lite on Bedrock costs fractions of a cent per parse.
- **The weekly report.** It reads the AWS database and mails through SES. On GCP it needs Cloud
  Scheduler, Cloud Tasks, a bucket, Eventarc and an e-mail provider. That is five services for one
  e-mail a week.
- **Lab 8 data (Athena, Glue).** It is an analytics exercise and not part of the app.

## Consequences

- **Two environments, one identity.** A user signs in with the same Cognito account on both sites,
  but data lives in two databases. The weekly report covers only the AWS one.
- **Secrets in state.** The generated password and the full database URL are in the `peach-gcp`
  state, as `google_client_secret` is in `peach-dev`'s (ADR 0007). Access to the workspace is
  access to the database.
- **No backups** on the Cloud SQL instance (they would be a second storage line). The data is a
  demo and is re-created by the migrations. A real deployment turns them on.
- **Migrations on start.** Every cold start runs `alembic upgrade head`, which adds about a second.
  `max_instance_count = 1` keeps two instances from migrating at once, and it also keeps the
  connection pool under db-f1-micro's ~25 connections.
- **Bootstrap by hand.** The project, billing link and budget alert are made in the console;
  `gcp/bootstrap` (local state) creates the service accounts and the workload identity pool, then
  HCP Terraform takes over. Workspace trigger paths keep `peach-dev` on `infra/` and `peach-gcp`
  on `gcp/`.
- **Lock-in moved, not removed.** The application code did not change. Lambda (Mangum, the
  `{"action": "migrate"}` event) and Aurora's IAM authentication were the AWS-specific parts, and
  they stay in the AWS deployment only. The lock-in is in the managed services around the core:
  Cognito, SES, Bedrock, EventBridge.
